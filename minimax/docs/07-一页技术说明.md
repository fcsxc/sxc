# 一页技术说明

> 规有所依 —— 面向软件持续演进的 SDD 上下文管理系统
> MiniMax × OceanBase 赛道

---

## 一、解决什么问题

在持续维护的软件项目里，需求规格、接口契约、设计决策、代码和测试都在演进。
AI 开发助手真正缺的不是「更多上下文」，而是**当前有效的上下文**：

- 哪些规格**现在还有效**（哪些已经作废）？
- 该改**哪些代码**（文件 / 符号）？
- 用**哪些测试**验证（新功能 + 兼容性）？
- 上一次做到哪了（跨会话、跨进程要能接上）？

本作品把这四件事做成了一个可运行的模块，并让三项技术在流程里真正承担职责。

## 二、模块结构

```
minimax/
├── sddctx/                     上下文模块（Python 包）
│   ├── config.py               路径 / 服务地址 / 模型配置（均可用环境变量覆盖）
│   ├── models.py               SpecItem / CodeSymbol / TestCase / TaskState / ContextPack
│   ├── importer.py             解析规格 front-matter、Python AST 符号、测试用例
│   ├── seekdb_store.py         seekdb 存取与检索（记录每一条执行的 SQL）
│   ├── selector.py             上下文选择算法（分词、打分、模块扩展）
│   ├── context_pack.py         上下文包渲染（Markdown / JSON）
│   ├── state_store.py          PowerContext 任务状态存取（HTTP API）
│   ├── agent.py                MiniMax 接入（提示词构造、输出解析、白名单写入）
│   └── cli.py                  命令行入口（import / context / state / agent / query / stats）
├── workspace/                  业务工程（被修改对象）：OrderFlow
│   ├── orderflow/              models.py / pricing.py / refund.py / service.py
│   ├── specs/                  9 条规格条目（含 active 与 superseded）
│   └── tests/                  16 个用例（目标功能测试 + 回归测试）
├── scripts/                    初始化、启动、验证脚本
├── snapshots/before/           修改前代码快照（用于复现「修改前失败」）
└── docs/                       运行说明、验证样例、技术使用记录、测试日志、开发记录、代码差异
```

调用入口只有一个命令：`python -m sddctx.cli <子命令>`（详见 `docs/01-运行说明.md`）。

## 三、上下文怎么选出来的

```
                      ┌──────────────────────────────────────────┐
   开发任务文本  ───▶  │ 1. 规格检索（seekdb）                   │
                      │    MATCH(search_text) AGAINST(task)      │
                      │    + 关键词 LIKE 兜底                    │
                      │    → 只取 status='active' 的条目         │
                      └───────────────┬──────────────────────────┘
                                      │ 命中规格的 applies_to
                      ┌───────────────▼──────────────────────────┐
                      │ 2. 焦点模块 = 任务点名的模块 ∪ 规格声明模块 │
                      └───────────────┬──────────────────────────┘
                                      │
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
   ┌────────────────────┐  ┌────────────────────┐  ┌────────────────────┐
   │ 3. 代码符号检索     │  │ 4. 测试用例检索     │  │ 5. 失效决策识别     │
   │ module_path IN(...) │  │ target_modules LIKE│  │ status<>'active'   │
   │ + 关键词匹配        │  │ + 关键词匹配        │  │ 且被命中规格取代    │
   └────────────────────┘  └────────────────────┘  └────────────────────┘
              └───────────────────────┬───────────────────────┘
                                      ▼
                      ┌──────────────────────────────────────────┐
                      │ 6. 上下文包（4 节）+ PowerContext 任务状态 │
                      └──────────────────────────────────────────┘
```

排序规则（可解释、可复现）：

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 数据库全文相关度 | 原值 | `MATCH(search_text) AGAINST(task)` 的返回值 |
| 关键词命中 | 1.2 / 个 | 标题、标签、正文中命中的分词数量 |
| 任务直接引用规格编号 | +8 | 任务里出现 `SPEC-XXX-XXX` 时命中 |
| 适用模块命中焦点模块 | +4 | 规格声明的 `applies_to` 与焦点模块相交 |

规格**每次都从数据库现查**，不做缓存，因此规格更新并重新导入后，输出立即使用新内容
（`scripts/verify_context.py` 会自动验证这一点）。

## 四、三项技术的分工

| 技术 | 在流程中承担的角色 | 具体落点 |
| --- | --- | --- |
| **seekdb（嵌入式 OceanBase）** | 存储工程资料或索引；**查询结果**用于构造任务上下文 | `spec_item` / `code_symbol` / `test_case` 三张表；`spec_item.search_text` 上的 IK 分词全文索引；检索用 `MATCH(... ) AGAINST(...)` + 按模块过滤的 SQL；所有执行的 SQL 记录在 `artifacts/context-queries.log` |
| **PowerContext** | 保存任务进展与验证结果，并在后续运行中读取、使用 | 状态以 Memory 条目（`kind=sdd-task-state`）写入 Scope；HTTP API：`POST /v1/scopes`、`POST /v1/memory/remember`、`POST /v1/memory/entries/list`；上下文包第 4 节直接呈现读回的状态 |
| **MiniMax** | 参与本次任务的代码生成与修改 | `sddctx/agent.py` 把上下文包 + 目标文件 + 只读参考文件 + 测试反馈组装成提示词，调用 **MiniMax-M3**（官方 HTTP API `chatcompletion_v2`，亦可切 `mmx` CLI / Anthropic 兼容协议），解析模型输出并**只写入白名单内的目标文件**；本次提交的实现即由该调用产出（提示词 21 334 字符，目标测试退出码 0），调用记录见 `artifacts/minimax-run.json` |

> 说明：MiniMax 凭据通过环境变量 `MINIMAX_API_KEY` 注入（未设置时复用官方 `mmx` CLI 的
> `~/.mmx/config.json`），仓库内不含任何真实凭据；
> 本次任务的代码修改由 MiniMax-M3 通过上述流水线完成，完整记录见
> `docs/05-MiniMax-开发记录.md` 与 `artifacts/minimax-coding-session.md`。

## 五、一次完整任务的流水

1. **导入**：`sddctx import` 把规格、代码符号、测试用例写进 seekdb（幂等，规格内容变化时 `revision` 自增）。
2. **取上下文**：`sddctx context --task "…"` 用真实 SQL 检索，产出规格 / 代码 / 测试 / 状态四节上下文包。
3. **写状态**：`sddctx state save --done … --todo …` 把进展写入 PowerContext。
4. **改代码**：`sddctx agent apply --target orderflow/refund.py --test-command "pytest …"`，
   MiniMax 依据上下文包产出修改，测试失败时把日志回灌重试。
5. **测**：`scripts/verify_before_after.py` 复现「修改前失败 / 修改后通过 + 回归通过」。
6. **复用**：模块重启后 `sddctx state show` 读回状态，并被下一次 `context` 使用。
